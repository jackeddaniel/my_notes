Kafka is a pipe with memory

A distributed, partitioned, replicated append-only log. Producers append events, consumers read at their own pace and keep their own bookmark. Work through each section, poke the labs, then test yourself at the end.

01

Why it exists

LinkedIn, around 2010: dozens of systems produce data (activity, logs, metrics, DB changes) and dozens need it (search, recommendations, Hadoop, monitoring, feed). Wiring each producer to each consumer gives N × M integrations. A shared log in the middle turns that into N + M.

What existed before

Gap: coupling

Point-to-point

HTTP calls, DB polling, nightly CSV/ETL. Tightly coupled, stale, each link custom.

Gap: scale, replay

Message queues

ActiveMQ, RabbitMQ, JMS. Delete on consume, per-message ack state on the broker, weak fan-out, slow when backlogged.

Gap: real time

Log aggregators

Scribe, Flume. High throughput, but batch shipping into HDFS rather than serving live consumers.

Kafka combined aggregator throughput, queue-style decoupling, and replay. Built at LinkedIn by Jay Kreps, Neha Narkhede and Jun Rao, open-sourced in 2011.

Problems it solves

  • Decoupling: producers don't know who consumes.
  • Buffering: spikes and slow consumers are absorbed by the log.
  • Fan-out: one stream feeds many systems independently.
  • Replay: rewind offsets to reprocess or bootstrap a new service.
  • Per-key ordering: same key → same partition → ordered.
  • Durability and scale: replicated partitions spread across brokers.
02

The log model

  • Topic: a named category of events (gps-pings, orders). Like a table.
  • Partition: an ordered, append-only, immutable log. Each record gets an increasing offset, counted per partition.
  • Retention by time or size, not by consumption. Reading doesn't delete.
  • Consumers track their own offset. The broker keeps no per-message delivery state, so replay is just "seek back".

Why disk-based and still fast

  • Sequential reads and writes only.
  • Leans on the OS page cache rather than its own cache.
  • Batching and compression.
  • Zero-copy sendfile from disk to socket.
Raft link: Kafka once needed ZooKeeper for metadata and controller election. It replaced that with KRaft, a Raft-based metadata quorum, and Kafka 4.0 removed ZooKeeper entirely.

What a record contains

  • key (optional): usually an entity ID; decides the partition.
  • value: payload bytes (JSON, Avro, Protobuf). Kafka never parses it.
  • timestamp and optional headers (trace ID, schema version).

Records are events: past-tense facts like OrderPlaced, not commands (SendEmail) and not mutable state (balance=500).

03

Partitions & replicas

A partition is a shard, not a copy. Each record lands in exactly one partition; together they hold the whole topic. Replication is a second layer: each partition is copied to other brokers.

Partitioning gives scale (data divided). Replication gives durability (each piece copied). Topic → many partitions; a partition belongs to exactly one topic.

04

Consumer groups

Many groups can read the same partition, each with its own offset. That's fan-out. Inside one group, each partition goes to exactly one consumer.

Why one consumer per partition per group

  • Progress is one number. The committed offset means "everything before this is done". That only works if one reader handles records in sequence. Two readers would need a per-message checklist, which is the bookkeeping Kafka removed to be fast.
  • Ordering. RideStarted and RideCompleted for one ride sit in one partition. Two readers could finish them out of order.

Analogy: a kitchen order roll is a partition. Each team (group) has one bookmark. Two cooks on one roll with one bookmark either cook the same order twice or need a claim list. To scale, add rolls (partitions), not cooks per roll.

Lab · assignmentPartitions are the parallelism ceiling

Share groups (KIP-932, "Queues for Kafka") are a newer opt-in for queue-style work: many workers per partition, per-message acks, no ordering. The classic group model is still the default.

06

Delivery semantics

A side effect (a push, a charge) and an offset commit live in two different systems. No ordering of the two is crash-safe by itself.

Lab · crash the consumerRecord at offset 9002: DriverAssigned
    GuaranteeHow you get itRisk
    at-most-onceCommit, then processMessages lost on crash
    at-least-onceProcess, then commit (default)Duplicates on crash
    effectively onceAt-least-once + idempotent processingNeeds a stable ID and care with the gap

    Making duplicates harmless

    • Dedupe on a stable ID: event_id or (topic, partition, offset) in a table with a unique constraint.
    • Same transaction: write the result and the offset to your own DB atomically; on restart, seek to the stored offset.
    • Idempotency keys for external APIs (payment gateways like Stripe and Razorpay support them).

    Kafka's exactly-once, and its boundary

    • Idempotent producer: producer ID + per-partition sequence numbers; the broker drops retried duplicates. On by default in modern clients.
    • Transactions: for consume → process → produce, output records and input offsets commit atomically. Readers use isolation.level=read_committed.
    • Boundary: only holds when input and output are both Kafka. Any external side effect falls back to idempotency.

    08

    Kafka or not?

    Kafka handles event streams, not time-series storage: no queries, order only per partition, timestamps can arrive late, data expires.

    The three-question test

    1. Is each message a fact that happened, not a job to do or a question to answer?
    2. Do multiple independent systems care about it, now or later?
    3. Is volume high enough, or replay valuable enough, to justify running it?

    Three yeses: strong fit. A "no" on the first is the clearest sign it's the wrong tool.
